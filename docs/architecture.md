# Architecture

Where content lives, how it gets into the app, and what the database is for.

## Decisions

- **Git owns the content.** Notes and the scripts generated from them live in a separate, private notes repo, not in this app's repo. Edits, history, and review all happen there.
- **Scripts live next to the notes** as `*.script.md` files, with the note they came from recorded in their header.
- **Scripts are generated by a skill, not by the app.** A `/script` skill inside the notes repo is run from Claude Code (using the existing subscription). The app never calls an AI model, so it has no per-run AI cost.
- **Postgres is a rebuildable cache plus app-owned data.** Everything derived from the repo can be dropped and re-synced. The database also holds things the repo cannot: listening progress, bookmarks, history, and later tags and playlists.
- **Script pages in the app are read-only.** To change a script, change the file in the notes repo.

## Notes repo layout

```
aipod-notes/
  notes/                     the user's markdown notes, any structure
  scripts/                   one *.script.md per note, same folder shape
  playlist.yml               optional play order
  .agent/skills/script/      the /script skill
```

A template of this layout lives in `notes-template/` in this repo.

## Script file format

A script is a markdown file with a header (frontmatter) and the spoken text as its body.

```
---
id: terraform-basics
title: Terraform basics
topic: Terraform
source: notes/terraform/basics.md
source_hash: 3f1c...   # git hash of the note when this script was written
model: claude-sonnet-5-5
skill_version: 1
status: draft          # draft until the user has read it, then approved
---
Spoken text starts here...
```

- `id` is stable. It never changes, even if the file is renamed, so progress and bookmarks follow the script.
- `source_hash` ties the script to one exact version of its note. If the note changes later, the hashes no longer match and the script is shown as **stale**.
- `status` is `draft` or `approved`. The user flips it after reading the script.

## Syncing the repo into the database

Only files that changed are written. Every file in a Git repo already has a content hash (its blob SHA), and GitHub lists all of them in a single call without downloading anything.

1. List every file with its hash (one call).
2. Compare with the hashes stored in the database.
3. Same hash: skip. New or different hash: download that file only. In the database but not in the repo: mark it removed (never hard-delete, so progress is kept).
4. Parse and validate the changed files. A bad file is reported and skipped; it does not stop the rest.
5. Upsert the valid ones. The upsert itself only writes when the hash differs, as a second safeguard.
6. Refresh the stored hash of each script's note, which is what makes a script stale.
7. Remember the commit that was synced.

Renames are matched by the script's `id`, not its path. Syncing never calls an AI model.

**When it runs:** a Sync button in the app and a `pnpm sync` command, plus an optional GitHub push webhook that triggers the same sync. The full comparison is always the source of truth, so a missed webhook cannot cause drift.

## Configuration

| Variable | Meaning |
| --- | --- |
| `NOTES_DIR` | Local folder to read instead of GitHub. Used in development. |
| `NOTES_REPO` | GitHub repo as `owner/name`. |
| `NOTES_REF` | Branch to read. Defaults to `main`. |
| `NOTES_TOKEN` | Fine-grained, read-only GitHub token for the notes repo. |
| `SYNC_WEBHOOK_SECRET` | Shared secret for verifying GitHub push webhooks. |
